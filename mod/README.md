# tiller mod

Per-node Claude Code mod. It does nothing unless `TL_NODE_ID` is set (with `TL_ENDPOINT`, `TL_TOKEN_FILE`, optional `TL_PARENT_ID`).
Every second it polls the daemon: `/tree` (the caller's whole tree, root first) feeds the band and toasts, and `/inbox` messages are delivered.
While a turn runs (from `turn.start` to its `turn.complete`) a message stays held in the daemon so its sender can still withdraw it; once the turn ends the mod claims it with `POST /claim` (a withdrawn or expired message fails the claim and is skipped), submits it with `$.prompt.submit` and acks it with `POST /ack` once the prompt is accepted. A steer (`send` with mode "now") is not held: the mod claims it, aborts the running turn with `$.turn.abort` and submits it at once. Should a `turn.complete` never arrive, the hold is released once `/tree` has shown this node `done` on two polls in a row. It forwards `turn.start`, `turn.complete` and `session.measure` to `/mod-event`.
It draws a one-line band above the prompt (in a child, `↑ parent` and `⌂ root` buttons; the needs-you child), and in-session toasts for children that need you, finish or error. The tree and node controls live in the app, not in Claude.
The mod is silent while a tiller client is attached. Every `/tree` and `/inbox` response carries `X-TL-Clients: app,browser` (the kinds of authenticated ws clients now connected, empty when none); when it is non-empty the mod keeps a `quiet` state atom true, the `AbovePrompt` hook passes through, and it makes no toasts and no `$.ui.log` lines, because the client's sidebar already shows all of it. Inbox delivery, acks, event forwarding and slash commands carry on. When the last client disconnects the band and toasts return, and the first diff after that is a baseline so changes made while quiet are not replayed.
In the chat each tiller message is one dim line: a received envelope (a prompt this plugin submitted whose text parses as a frame, nonce matched on its start and end lines) as `↘ message from <sender> · steer · reply-to <id>`, and the agent's own `mcp__tiller__send` call as `↗ message to <title> (<id>) · <outcome>`, its result block hidden unless the outcome is other than `queued` or `delivered`. ctrl+o (or `--verbose`, or an export, or a surface that does not say whether a tool row is expanded) draws them in full; an errored or interrupted send is never compacted. These `UserMessage`, `ToolUse` and `ToolResult` render hooks change the drawing alone: the stored prompt and what the model reads are untouched. The outcome is the one the call returned (usually `queued`), not later delivery.
The daemon loads it by launching `claude --plugin-dir <repo>/mod ...` with the TL_* variables in the environment.
Commands: `/tl-list`, `/tl-spawn <title> :: <prompt>`, `/tl-send <nodeId> <text>`, `/tl-read <nodeId>`.
The four call the daemon's `POST /api/<tool>` with the node's token and print the text result.
The band's `↑ parent` and `⌂ root` buttons POST `/focus {id}` (any node in the same tree); the daemon broadcasts it and a `tl` client showing that node switches to the target.
Source is TypeScript under `hooks/`: `register.tsx` holds everything that uses `$`; `api.ts`, `notify.ts`, `commands.ts`, `rows.ts` and `band.tsx` are pure helpers (the validator forbids passing `$` to imported functions).
Check with `claude plugin validate mod/` and `claude plugin test mod/`; the quiet behaviour and the hold during a turn are tested against a stub daemon in `mod/tests/quiet.test.tsx` and `mod/tests/hold.test.tsx`, and the compact rows in `mod/tests/rows.test.tsx`.
The mod sends no OS notifications: the daemon is the single sender (see docs/frontends.md), so the app and the terminal never both notify.
