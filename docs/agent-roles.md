# Agents: what they are told and how their work is checked

## The system prompt

Every Claude node is launched with text appended to Claude's own system prompt, so it survives `/clear`. It has two parts. The preamble, generated by `systemPrompt` in `src/daemon/launch.ts`, gives the node its id, title and parent, explains the message envelope (see [messaging.md](messaging.md)), tells a node with a parent to finish with `report_outcome`, and adds a paragraph about the session directory and, for a worktree node, about its worktree. The role section follows it under a `# Role` heading.

## Role prompts and overrides

A node's role is `orchestrator`, `worker` or `none`. By default a root node is an orchestrator and a node with a parent is a worker; `--role` on `tl new` and `tl spawn`, or `role` on the MCP `spawn` tool, sets it explicitly, and `none` leaves the role section out.

The role text is the built-in default (`DEFAULT_PROMPTS` in `src/daemon/launch.ts`) unless an override file exists. A file at `<repo>/.tiller/orchestrator.md` or `worker.md` wins for nodes whose directory is that repo; otherwise `~/.tiller/prompts/orchestrator.md` or `worker.md` applies to every repo. The files are read at each launch or resume, so an edit applies to the next node you start. `tl prompts` prints the files in effect for the current directory, or `built-in` where there is none.

The built-in orchestrator prompt tells the orchestrator to coordinate rather than do the work: split a task into independent streams, spawn one worker per stream with a self-contained brief, wait without polling, read each worker's outcome, have non-trivial changes reviewed by a node with the `reviewer` preset (at most two rounds before asking the human), check the diff, merge, and close finished workers. The built-in worker prompt tells the worker to do exactly its brief and to ask its parent, not the human, when the brief is unclear.

## Model, effort and permission mode

A node spawned without a model or effort gets the ones in the config's `roles` key for its role (a node with role `none` counts as a worker), and keeps them across restarts. Effort is passed to claude as `--effort`. A spawn without a permission mode inherits its parent's, except that `bypassPermissions` is never inherited, and only the human may spawn a node with `bypassPermissions`. The order is: explicit spawn arguments, then the preset, then the config's `roles`.

## Presets

A preset is a named kind of node: a markdown file at `<repo>/.tiller/agents/<name>.md` or `~/.tiller/agents/<name>.md`, the repo file winning. `tl spawn --preset NAME`, `tl new --preset NAME` and `preset` on the MCP `spawn` tool use it, and `tl presets [--cwd P]` lists the presets in effect for a directory and the file each comes from. The file is read again at each launch or resume, and `list_nodes` shows a node's preset.

The frontmatter takes the fields of a Claude Code agent definition that Claude enforces (`model`, `tools`, `disallowedTools`, `permissionMode`, `maxTurns`; `name` and `description` are informational) plus tiller's own `effort`, `isolation` and `role`. The body replaces the role prompt text.

```markdown
---
description: Answers with a code word, on a cheap model.
model: haiku
effort: low
tools: Read, Grep, Glob
disallowedTools: Bash
---
# Greeter

Answer every request with the code word "marmalade" and nothing else.
```

`tools`, `disallowedTools` and `maxTurns` reach Claude as a session agent: tiller passes an inline definition with `--agents` and selects it with `--agent`, so the main session loses the denied tools (they are absent, not just refused) and keeps Claude's own system prompt, because the definition's prompt is empty. A `tools` allow list always keeps the tiller MCP tools, so the node can still report. Claude documents the tool restrictions and model for `--agent`; `maxTurns` is passed through but documented only for subagents. `model`, `effort` and `permissionMode` go to claude as the usual flags.

The daemon writes two built-in presets into `~/.tiller/agents/` on start, and never overwrites a file that exists, so your edits stay:

- `reviewer` reviews a worker's branch against its brief, runs the checks and reports findings through `report_outcome` without fixing anything. It has no Edit, Write or NotebookEdit, effort medium and no worktree. It runs in the default permission mode rather than plan mode, because plan mode makes Claude ask the human before every tiller tool call, `report_outcome` included; without Edit and Write, default mode still asks before any shell command that would change files, unless your own Claude settings allow it.
- `researcher` answers a question from code and the web. It has only Read, Grep, Glob, WebSearch and WebFetch, so no shell.

## Spawn limits

An agent's spawn is refused when the new node would sit more than `limits.maxDepth` levels below its root, when its parent already has `limits.maxChildren` live children, or when `daemon.maxLiveNodes` nodes are live. The error names the limit and tells the agent to reuse an idle worker or close finished ones. The human's spawns are exempt.

## report_outcome

A worker ends its task by calling `report_outcome` with `succeeded` or `failed`, an optional `note`, and the structured fields `summary` (what it did), `changedFiles` (paths), `verified` (what it ran to check the work, and the result) and `openQuestions` (what is left for the parent to decide). The parent reads these from `list_nodes` instead of reading the transcript; the app shows them in the last-message panel and on the exited card, and the multiplexer shows the outcome and summary under an idle node. The daemon tells the parent of every recorded outcome (see [messaging.md](messaging.md)).

## The completion gate

The `gate` config key makes a `succeeded` report wait for a check, for example `{"gate": {"command": "npm test"}}`. The daemon runs the command with `sh -c` in the worker's directory, with the daemon's login PATH and `TL_NODE_ID` in the environment (plus the worktree variables of [worktrees.md](worktrees.md) for a worktree node), and appends its output to `~/.tiller/nodes/<id>/gate.log`; the node shows "gate: <command>" meanwhile and its row carries a gate marker. The gate runs only when Claude already trusts the directory. A worktree node reads the key from the main checkout's project file.

If the command passes, the outcome is recorded with `gate: "passed"`. If it fails, nothing is recorded and the worker is told, with the last 60 lines of output, to fix the problem and report again. The reply to `report_outcome` carries the result when the gate finishes within 30 seconds; otherwise the reply says the gate is pending and a failure arrives later as a message. Any report made while the gate is still running is refused. After `gate.retries` further failures the outcome is recorded as failed with `gate: "failed"`. Each run is stopped after `gate.timeoutMinutes`. `tl gate [--cwd P]` runs the configured command once in a directory and prints the result, so you can try it.
